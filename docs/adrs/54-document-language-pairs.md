# ADR-54: A document language pair is an explicit, confirmed link between two files

**Status:** Accepted. Phase 8 of the Brain rebuild; it ships in small pull requests behind a feature key (ADR-50).
**Date:** 2026-10-06

## Context

A knowledge base often holds the same document twice, once per language: a Polish policy and its English version. Nothing in Ragen knows they are the same document. Three screens suffer from that. Brain › Documents lists both files and counts their knowledge twice, so a reviewer approves the same fact in two languages. The Brain graph shows two clusters for one subject. And the PII policy of the two files can differ without anyone seeing it, so a document masked as `STRICT` in Polish can be retrieved unmasked from its English twin. The handoff brief asks for pair grouping, a merged graph cluster, a "same content in EN" link in review mode and a PII inconsistency card, and it requires an ADR first because the schema has nothing to hang this on.

What exists today, measured on `main`: `UserFile.language` is an ISO 639-3 code from franc, set by the worker and copied to every Qdrant chunk, and null when detection is not confident (spreadsheets, short text). The language spec lists translation and cross-language retrieval as non-goals, and `document-summary.ts` states that language groups "have no pairing semantics". `UserFile` already has a self-relation, `sourceFileId`, but it means "this is an import of that knowledge-base file" and retrieval reads through it, so it cannot be reused. `piiPolicy` is `NONE | TOXIC_ONLY | STRICT`, declared in that order, and no code compares two policies. The single-file and bulk policy commands accept any value, lowering included; the brief's "never lower automatically" is therefore a rule for the new feature, not an existing invariant. File access goes through one predicate, `fileAccessWhere(actor)`, which callers combine with `organizationId`. The document summary is stored in plaintext in `UserFile.metadata.summary` and also as a searchable Qdrant chunk with `chunk_type: 'summary'`, which carries `accessible_by`. Merging Brain pages is one command, `mergeKnowledgePagesCommand`, which absorbs only a candidate and refuses published pages. Nothing in code, schema or specs models a counterpart or a translation.

## Decision

A pair is an explicit link between two files of the same organization, created by a person who can manage both. Ragen may suggest a pair but never creates one on its own, and a suggestion is computed when asked for and never stored.

The link is a new table, `DocumentPair`, not a column on `UserFile`. A row holds `organizationId`, and two file ids stored in a fixed order (the smaller id first) so that a pair has one representation and cannot exist as both A→B and B→A. Both ids reference `UserFile` through the existing `(id, organizationId)` unique key, which makes a cross-organization pair unrepresentable. Each file may appear in at most one pair, and the database enforces that across both columns, including a file that is the smaller id in one pair and the larger in another: a second table, `DocumentPairMember`, holds one row per file with `file_id` as its primary key, so a file cannot be a member of two pairs and two people pairing the same file at once cannot both succeed. Its rows belong to the pair (cascade from `DocumentPair`) and to the file (cascade from `UserFile`, through the same `(id, organizationId)` key), and the create command writes the pair and both members in one transaction. A pair is exactly two files in this version; a group of three languages is a later extension of the member table, not of this decision. Deleting either file deletes the pair, which deletes both members, and leaves the other file untouched. A Brain vehicle file cannot be paired, matching the rule that it is neither listed nor deletable. Language is not a precondition for pairing, since detection returns null for exactly the files people most want to pair, but when both languages are known and equal the UI says so before confirming.

Suggestions come from the summary chunk, not from file names. For a chosen file the suggestion query searches Qdrant for `chunk_type: 'summary'` points whose language differs, filtered by `organization_id` and by the caller's `accessible_by`, and returns the nearest few with a similarity score. The caller then confirms one. This reuses the ADR-16 summary and the existing hybrid index, adds no new embedding job, and needs no payload change.

Access follows the file, never the pair. A pair row reveals that a counterpart exists, and a file name alone confirms a document, so every query that follows a pair applies `organizationId` and `fileAccessWhere(actor)` to the far end. A user who can read only one side sees an unpaired file. Creating or removing a pair requires the manage-documents capability on both files, checked by capability, never by role string.

The PII rule is the one in the brief, now stated precisely. When a pair is created, or when either file's policy later changes, and the two policies differ, Ragen shows the inconsistency and offers one action: raise the weaker file to the stricter policy. It never lowers a policy, and it never changes one without a click. Raising reuses the existing policy command and the existing "reprocess" step, because a policy change does not alter chunks that are already indexed. The inconsistency card on the knowledge list is computed from pairs and policies on read.

Brain does not get a second way to merge. Pair rows in Brain › Documents group two files under one line and count the union of their pages once. "Merge pairs" in the graph and "same content in EN" in review mode only propose candidates to the existing `MergePicker` and run the existing merge command, with all its refusals: published pages are not merged, access becomes the narrower of the two, and the absorbed page is superseded. Anything that follows a merged page, such as open questions to an owner or citations recorded by an answer, therefore keeps one path to follow.

## Consequences

The schema gains one table and one migration, additive, with no change to `UserFile`; rolling the feature back means switching its feature key off, and the table stays unused. Because `UserFile` is untouched, the import relation, the Qdrant payload and the worker are unaffected, and retrieval does not change: a pair does not make a Polish question retrieve English chunks, which stays out of scope as in the language spec. The feature ships behind a feature key defaulting to `false` and in small pull requests per ADR-50: the table and commands, then suggestions, then the knowledge-list toggle and PII card, then the Brain views.

The cost is that pairs are only as complete as people make them. A knowledge base nobody pairs shows no grouping and no inconsistency card, and the PII gap this ADR describes remains for those files. Suggestions reduce that cost but do not remove it. A computed-only pairing would need no table and no confirmation, but it would show wrong groups with no way to correct them, would make the PII card a guess, and would hand the merge picker pairs nobody approved, so it was rejected. A `counterpartFileId` column on `UserFile` is the smallest change, but it is asymmetric (A can point at B while B points elsewhere), allows at most one pair per file only by convention, and sits next to a self-relation that already means something else, so it was rejected in favor of a table whose shape enforces the rule.

Two things are deliberately left open. The "never lower" rule is enforced only inside the pair flow; the existing single and bulk policy commands still allow lowering, and tightening them is a separate decision. And the summary is plaintext in `metadata`, so a suggestion shows file names and a score but never summary text beyond what the file list already shows.
